背景：`docs/handoff-gaode-verify.md` 已经做完，结果在该文件末尾的「结果」一节。数据在 `reference/timetable-gaode/`。这次改 `src/sim/`，只改**工作日**，双休日不动（还没有周末数据）。

先看：`docs/design-decisions.md` 的 D72–D75，以及 `src/sim/timetable.ts` 的 `dayPeriods`、`generatePlan`、`circulate`、`standbyWindows`。

## 对照工具

```
npx tsx scripts/gaode-compare.ts                              # 检查站汇总
npx tsx scripts/gaode-compare.ts --table 北新泾,世纪公园,张江高科  # 逐 15 分钟 高德/计划
```

比的是每 15 分钟可上车的班次数。检查站只用互相一致的五列：北新泾往西、世纪公园双向、张江高科双向。高德有几处站点数据本身对不上邻站，不拿来当目标：虹桥2号航站楼往西午间、北新泾往东 18–21 点、广兰路以东各站。一格差 2 班及以上算不合格。

改之前的基线：两个时间窗（06:00–11:00、16:00–23:30）里有 60 格不合格，绝对差合计 206。

## 要改什么（模型 vs 高德）

总班数基本对得上，问题是分布在错的时段。

### 第一段：早高峰

| | 高德 | 现在的模型 |
|---|---|---|
| 进入 2'30" | 北新泾往东 06:45；世纪公园往西 06:45（龙阳路始发先加密）；张江高科往西 06:56 以前 6–8 min 一班，07:03 起 2'30"；北新泾往西约 07:45 | 世纪公园往西 06:00 就是 2'30"，张江高科往西 06:45 |
| 进入以前 | 06:15–06:45 核心约 3'45"–5' | 06:05 起 5' |
| 退出 | 2'30" 保持到约 10:00（北新泾往东 09:45，世纪公园/张江高科往西 10:00） | 09:30 |
| 退出以后 | 10:00–10:45 约 3'30"–4'，10:45–11:00 回到 5' | 直接回到 5' |

我试过一次：只把 `weekdayAM` 改成 07:40–10:00，把 `standbyWindows` 的 09:30 改成 10:00。结果是：

- 校验剩 3 个 error：广兰路 07:29 `TURN_HEADWAY`，蟠祥路 08:00 `TERMINAL_FULL`，浦东机场 10:29 `TERMINAL_FULL`；
- `fleetPeak` 从 81 升到 87；08:00 在线 82 列，稳定以后是 74 列。原因是早高峰前 5' 一班的大交路车已经在线上，进入高峰时没接上新时隙，又从车辆段另出了车。

另外试过高峰后加一段全大交路的 210→300 s 过渡，车队到 88，终点站更挤。高峰后的过渡要保留 2:1 大小交路，外段维持 5'，只让核心间隔渐长，参考 `weekdayPMTail` 的写法。

### 第二段：晚高峰

| | 高德 | 现在的模型 |
|---|---|---|
| 进入 3' | 张江高科往西 17:30，世纪公园往西 17:30，北新泾往西 17:45，世纪公园往东 17:45，张江高科往东 18:00；16:00–17:15 还是约 5' | 世纪公园、张江高科往西 15:45 就是 3'，世纪公园往东 16:30 |
| 退出 3' | 往西约 20:30（世纪公园、张江高科）；往东到约 21:30（世纪公园、张江高科） | 19:30 起 165→240 s，20:55 收小交路 |

`weekdayPM.from` 现在是 16:50。按 `coreLead` 的口径，它表示「整个核心段都已经进入高峰」的时刻，参考站在这之前约一个核心段全程就已经开始加密了。所以要往后挪一个多小时，不是挪几分钟。

### 第三段：夜间

| | 高德 | 现在的模型 |
|---|---|---|
| 21:30–23:00 | 核心约 4' 一班（世纪公园双向每 15 分钟 3–4 班；北新泾往西到 23:45 还是 3–4 班） | 21:40 起 480 s |
| 往东 22:30 以后 | 世纪公园 4 班 / 15 min，张江高科 2 班 | 两站相同 |
| 往西 22:00 以后 | 世纪公园 4 班 / 15 min，张江高科 3 班 | 两站相同 |

【推断】往东一半的车在龙阳路终到，大概率是载客回龙阳路车辆段。往西有些车从龙阳路始发。

晚上 4' 一班要的车比现在多，回段顺序、过夜存车都要跟着重排。

### 午间外段：不改

虹桥2号航站楼往西、唐镇、东段都没有证实是真车，见 verify 文件的「结果」一节。

## 已知的耦合点

挪时段不只是改 `dayPeriods`。下面这些写死的时刻和窗口要一起看：

- `standbyWindows`（`timetable.ts:146`）：热备窗口 09:30 / 15:00 / 19:30 / 20:55–21:40。
- `circulate` 里的 `H(7)`、`H(8)`、`H(10)`（约 `:1095`、`:1104`、`:1121`），以及 `fitOpeningFeeders` 的 `H(10)`（`:1533`）。
- D72 的小交路收车：`H(20, 55)`、`H(20, 50)`–`H(21)`（`:399`、`:483`–`:495`）。
- D74 的夜间运行等级：`dwellFactorAt` 的 `H(21)`（`:239`），`plannedRunLevel` 的 21:10 / 21:25（`:246`）。这几处是按官方末班标定的，末班时刻不能因此走偏。
- D75 广兰路中间线：开班时隙的 `gllCycle`，早高峰挪了以后要重看。
- `OVERLAY_PRESETS` 的进博会 09:30–17:30、虹桥枢纽 20:00–22:30：起止时刻不用改，但要确认在新图上还能排得出来。
- 首末班：`OPERATIONS` 的首末班常量、`src/data/firstlast.ts` 不动。

## 做法

1. 一段一停：先早高峰，再晚高峰，最后夜间。每段做完就停下来汇报，等审，审过了再开始下一段。
2. 每段都写一个 D 条目，从 D79 开始编号。
   - 从高德数据推出来的标【假设】，写清楚依据哪个文件、哪几格。
   - 推翻了 D72 的哪一段，写明「推翻 D72 的……」。
3. 只改运行图结构：时段、交路、出入段、热备、存车。走行时分、停站模型、运行等级参数、`OPERATIONS` 的首末班常量都不动。
4. 编图修不过去的冲突，宁可让那一格跟高德差一班，也不要硬塞车。差在哪、为什么，写进汇报。

## 每段的完成标准

- `npx tsx scripts/validate-plan.ts weekday` 和 `weekend` 都是 0 error。
- `scripts/gaode-compare.ts`：本段时间窗内的检查站，不合格格数比基线明显下降（目标是本段内不超过 4 格），并且没有差 3 班及以上的格。
- 车队和库位：`fleetPeak` 不超过 92；`yardNeed` 不超过北翟路 36 / 龙阳路 24 / 川沙 32。在线车数曲线和改前对比，列出来。
